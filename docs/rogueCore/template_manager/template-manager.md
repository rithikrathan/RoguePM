# Template Manager

The Template Manager is the Rogue Core subsystem that tracks, validates, and applies project templates on the local node.

A **template** is a self-contained blueprint for scaffolding a specific language or tool environment. It contains a dynamic generator script and a folder of static starter assets.

---

## What Templates & Template Manager Do

### Role of a Template
- Generates project-specific starter code and build configurations.
- Copies unchanging boilerplate files into the target project folder.
- Does not touch Git, remotes, or terminal sessions.

### Role of the Template Manager
- Tracks all templates on the local machine in the Sled database.
- Periodically crawls the template directory to discover new, updated, or removed templates.
- Filters templates by active Intent domain when scaffolding.
- Dispatches template execution safely through the Shell Abstraction Layer (SAL).

---

## Inputs & Outputs

### Inputs (Passed to `<template_name>.sh`)
The runner executes the generator script with three standard arguments:
- `-n <project_name>`: The name of the project being created.
- `-l <license>`: The chosen license slug (e.g. `mit`, `apache-2.0`).
- `-m <message>`: The initial commit/description message.
- Target execution directory: The script runs with the target project directory as its current working directory (`pwd`).

### Outputs (Produced in Target Directory)
When applied, the template produces two categories of files:
1. **Dynamic Files (Generated by `<template_name>.sh`):**
   - `LICENSE`: Fetched live via GitHub API (`gh api "/licenses/$LICENSE"`).
   - `README.md`: Generated with the project name and description.
   - Build configs: Project-specific build files populated with the project name (e.g., `CMakeLists.txt`, `Cargo.toml`, `package.json`, `Makefile`).
   - Starter code: Entrypoint source files (e.g., `src/main.c`, `src/main.rs`, `main.go`, `sketch.ino`).
2. **Static Files (Copied from `files/`):**
   - `.gitignore`: Default language/tool ignore rules.
   - `TODO.md`: Starter task list.
   - Static assets: Fixed headers, schematics, or config boilerplate copied without modification.

## Architecture & Scope
- **Directory Structure:**
  ```text
  templates/<template_name>/
  ├── <template_name>.sh    # Generator script
  └── files/                # Static assets folder
      ├── .gitignore
      └── TODO.md
  ```
- **Execution Boundary:** Templates only generate code and copy assets. Rogue Core handles directory creation, `git init`, initial commits, cloud remotes, and `session.sh`.
- **Database Indexing:** Tracked in local Sled under `tmpl:<template_id>` with path, script name, and Intent mappings.
- **Intent Scoping:** Filtered by active Intent domain by default, with a global list override (`--all`).
- **Template Stacking (*):** Experimental proposal to layer multiple templates sequentially. Unfinalized.

## Lifecycle Stages

### 1. Creation
- Manual authoring. The user copies an existing template folder or manually creates `<name>.sh` and `files/`.
- Templates reside strictly on the local node.

### 2. Registration & Crawling
- The Template Manager periodically crawls the templates directory, tracking three states:
  - `unregistered`: Newly found folder on disk, pending user review and intent assignment.
  - `registered`: Active template confirmed on disk.
  - `missing`: Registered in database, but directory was removed from disk.

### 3. Management
- Direct disk execution. No database file-versioning or content tracking.
- Users can update linked Intent domains or toggle templates hidden from pickers.

### 4. Selection
- Rogue Core initiates template selection during project creation (`-t` flag or fuzzy picker) and queries Template Manager.
- Scoped to active Intent by default.

### 5. Execution Order
1. Generator script runs first via SAL with input arguments (`-n`, `-l`, `-m`).
2. Static files from `files/` are copied second, allowing boilerplate to cleanly override or fill layout.

### 6. Cleanup
- When a folder is deleted, the crawler marks its record as `missing`.
- Users purge `missing` records to clean up the database.
